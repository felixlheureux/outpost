# GitHub Issue source and mutation contract

OP-004 projects issues from the selected repository through the host service user's existing `gh` login. It does not store a token or alter repository files. `GET /api/v1/projects/:id/issues` returns cached issue identity, title/body, open/closed source state, content digest (SHA-256 of title, a NUL separator, and body), fetched time, local revision, parsed requirements, parse error, stale flag, and source health. `POST /api/v1/projects/:id/issues/sync` performs a bounded full read. Visible Queue views poll the local projection every 30 seconds and offer manual Sync. A failed read retains prior observations. A row omitted from a successful full listing remains cached with `stale: true`; omission is not proof of deletion.

Ordinary issues use their title/body as the objective. `##` and GitHub issue form `###` sections named Outcome, Acceptance criteria, Implementation notes, and Outpost settings are recognized. The optional settings section accepts one fenced YAML document with `outpost_task: 1`, `kind: implementation`, up to 50 distinct same-repository issue-number dependencies, optional `hold_reason`, `check_profile`, `delivery`, and `review`. Unknown fields, duplicate blocks/keys, cycles, missing or invalid dependencies, and unsafe policy values yield an issue-specific parse error. No source text can define shell commands or credentials. Until project check-profile configuration is delivered, only `check_profile: inherit` resolves; named profiles are blocked visibly.

Issue create: `POST /api/v1/projects/:id/issues`. Edit: `PATCH /api/v1/projects/:id/issues/:number`. Each JSON body contains `request_key`, `title`, and `body`. Edit also contains `expected_digest` and `expected_revision`. The client generates one stable request key for a submitted draft and reuses it for inspection after a lost response. The server persists the operation and its source/draft identity before a GitHub write. The operation receipt returns `id`, key, kind, state (`pending`, `confirmed`, `rejected`, `conflict`, or `unknown`), source/result issue number, reason, and creation time. `GET /api/v1/projects/:id/issue-operations` lists the latest 50 receipts, `GET /api/v1/projects/:id/issue-operations/:key` reads one, and `POST /api/v1/projects/:id/issue-operations/:key/inspect` checks an uncertain remote effect without replaying it. Repeating a key with different content is rejected.

A create/edit appends a hidden `outpost-issue-operation` marker. After writing, Outpost re-reads the issue. An uncertain create searches the bounded issue listing for that marker before it can be confirmed; absent or ambiguous evidence stays `unknown` and is never automatically replayed. An edit compares the cached digest/revision and a fresh GitHub read before PATCH, then re-reads after. Conflicts retain the client draft for comparison. GitHub Issues PATCH has no manifest SHA compare-and-swap: a concurrent writer between pre-read and PATCH can still win or be overwritten. The receipt reports the observation, not an atomic update guarantee.

Closed issues are projected as externally closed/unverified; this source layer does not claim checks or local completion. Source refresh does not create another execution generation. OP-005 consumes these issue numbers for the one-file queue; OP-007 captures immutable assignment source snapshots and enforces admission. A real signed-in account read/create/edit journey remains separate from fixture verification.
